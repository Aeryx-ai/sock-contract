# sock v1 API contract

Pass 11: puppet deliveries are leased and owners see when a puppet was last heard ([puppet inbound](puppet-inbound.md)). Pass 10: feature flags and the registration policy ([feature flags](feature-flags.md)). Pass 9: `HistoryTransferService` moves a phone's history to a desktop. Pass 8. Request and response shapes live only in [`proto/sock/v1`](../../proto/sock/v1); this file holds what proto cannot say. Transport: Connect RPC over HTTPS: production at `https://api.joinsock.com` (`https://api.sock.aeryx.ai` is an alias until removed). JSON or protobuf. Path `/<package>.<Service>/<Method>`, always `POST` (`Subscribe` is a server stream).

## Operational

`GET /healthz`: unauthenticated, on the public listener, returns 200 when the database answers, 503 otherwise. Used by Render's and the container's health checks only; carries no data.

Sign in with Apple on the web, for `sock login`, the operator console and `sock-admin login`, which shares the `cli` routes. All anonymous, on every listener, no database or Apple call, not rate limited by sockd. All answer `404` when `SOCK_APPLE_SERVICES_ID` and `SOCK_APPLE_WEB_REDIRECT_URI` are unset. Every response carries `Cache-Control: no-store` and `Referrer-Policy: no-referrer`; no route's query string or body is logged. A malformed request gets a fixed `400` page and no redirect.

Anonymous, on every listener, no database or WorkOS call, not rate limited by sockd. Both answer `404` when `SOCK_WORKOS_DESKTOP_REDIRECT_URI` is unset or WorkOS (`SOCK_WORKOS_CLIENT_ID`, `SOCK_WORKOS_API_KEY`) is not configured; the app reads a `400` for `GET /workos/desktop-login` with no query as configured. Nothing logs their query string. Anything that breaks a rule below is the fixed `400` (`bad request`, plain text, no redirect, nothing echoed). Terminal sign-in, for `sock login` ([terminal sign-in](terminal-sign-in.md)): the hub's own code page, then AuthKit, then a hub callback that redeems the code itself; the terminal polls `FinishTerminalSignIn` and never listens. Anonymous, on every listener. All three answer `404` unless WorkOS (`SOCK_WORKOS_CLIENT_ID`, `SOCK_WORKOS_API_KEY`) is configured and the hub host (`SOCK_APPLE_WEB_REDIRECT_URI`'s) is known. Every response carries `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and `Content-Security-Policy: default-src 'none'; style-src 'self'; img-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`. Nothing logs a code, a cookie or a query string; the routes log the sign-in id and the outcome. Anything that breaks a rule below is the fixed `400` page, nothing echoed.

|---|---|---|
| `GET /login` | Optional `code`, up to 64 characters; after uppercasing and dropping spaces and dashes, a match for `^[BCDFGHJKLMNPQRSTVWXZ]{8}$` fills the form's input, anything else leaves it empty. No database, not rate limited | `200` page: "Enter the code shown in your terminal", one form posting `code` to `/login`, and the warning to continue only for a `sock login` the person just ran |

| `GET /workos/terminal-callback` | WorkOS's redirect: `state` (a UUID), and either `code` (1 to 512 printable ASCII) or `error` matching `^[a-z_]{1,64}$`, never both; `error_description` and other parameters ignored. Counted downloads ([downloads](downloads.md), sock-server ADR 53): the hub counts a release file's fetch by asset and UTC day in the `analytics` schema and sends the browser to the bucket. Anonymous, on every listener, its own limit. Every response carries `Cache-Control: no-store` and `Referrer-Policy: no-referrer`; nothing logs the request beyond the asset key.

| Route | Request | Response |
|---|---|---|
| `GET /download/<key>` | `<key>` matching `^releases/[a-z0-9-]+/[A-Za-z0-9._+-]+/[A-Za-z0-9._+-]+$`, at most 512 bytes; any other path under `/download/` is `404`, nothing echoed. 60 a minute per client network, burst 20, in each replica's memory; past it `429` with `Retry-After` | Records one download of the asset on the UTC day, then `302` to `<SOCK_DOWNLOADS_URL>/<key>` (default `https://downloads.joinsock.com`). A failed record is logged; the redirect goes regardless |

Stripe webhooks, for Sock Pro ([Sock Pro billing](sock-pro-billing.md)). Caller Stripe, on every listener, not rate limited by sockd, no CORS. Mounted only when `SOCK_STRIPE_SECRET_KEY` (a restricted key: write Checkout Sessions, Customers and Customer Portal sessions; read Subscriptions and Prices), `SOCK_STRIPE_WEBHOOK_SECRET` (the endpoint's `whsec_` signing secret) and `SOCK_BILLING_RETURN_URL` are all set, else `404`; the facts are recorded whether or not `SOCK_PRO_REQUIRED` enforces them. Stripe's endpoint is `https://<hub host>/stripe/webhook` with events `customer.subscription.created`, `.updated`, `.deleted`, `.paused`, `.resumed`, `customer.deleted` and `checkout.session.completed`. Logs carry the Stripe event id, type and outcome; never the body.

| Route | Request | Response |
|---|---|---|
| `POST /stripe/webhook` | Stripe's event JSON, body at most 64 KiB, with `Stripe-Signature` verified by `Billing.VerifyEvent` (domain model): `t` within 5 minutes of now and a `v1` HMAC-SHA256 over `t.payload` under `SOCK_STRIPE_WEBHOOK_SECRET`, compared in constant time. Only `type` and the object's `id` (and `customer` for `customer.deleted`) are read; nothing else in the payload is trusted | `200`, empty, once applied or ignored. `SubscriptionChanged` (the `customer.subscription.*` types, and `checkout.session.completed` for its `subscription`): one transaction takes `pg_advisory_xact_lock` on the subscription id, fetches it (`Billing.Subscription`, 10 s), then `Account.ApplySubscription(snapshot)` for the human whose billing customer Stripe names, so two deliveries for one subscription never write an older fetch over a newer one. `CustomerDeleted`: deletes the billing customer and its subscriptions. Each emits `ProEntitlementChanged` when it moves `ProActiveUntil()`. Ignored, still `200`: an unknown event type, or a subscription whose customer is no human's. `400`: a missing, malformed, stale or mismatched signature. `500`: the fetch from Stripe or the write fails, so Stripe retries (for 3 days). Idempotent: each delivery fetches the current state and writes it, so duplicates and out-of-order deliveries converge |

OAuth 2.1 authorization server for agent platforms. The resource server, `sock-mcpd` at `SOCK_CONNECTOR_RESOURCE`, serves its own RFC 9728 metadata and is specified in `sock-integrations`; the hub serves only the routes below. Enabled only when `SOCK_OAUTH_SIGNING_KEY`, `SOCK_OAUTH_KEY_ID`, `SOCK_CONNECTOR_RESOURCE`, `SOCK_APPLE_SERVICES_ID` and `SOCK_APPLE_WEB_REDIRECT_URI` are all set; otherwise every route answers `404` and the two connector RPCs `CALLER_NOT_ALLOWED`, and sockd refuses to start with `SOCK_OAUTH_SIGNING_KEY` set and any of the others unset. On every listener; `<hub host>` is the host of `SOCK_APPLE_WEB_REDIRECT_URI` (as for the console sign-in nonce), never the request's `Host`, and `iss` is always `https://<hub host>`. No route logs a code, token, verifier, nonce, id_token, cookie, consent token or Apple `sub`; authorize, consent, token and revoke log client id, grant id and outcome. Bodies are at most 16 KiB; more is the route's malformed answer. Rate limits: Rate limits, below. JSON errors are RFC 6749 §5.2 objects whose `error_description` is a fixed string, never request data. A fixed error page is one constant page with no link back to any client.

## Caller classes

| Class | Authenticates with | Trusted to assert | Never trusted to assert |
|---|---|---|---|
| Anonymous | Nothing. | Puppet device | `Authorization: Bearer sock_pt_…`. A connector puppet's token, held by `sock-mcpd`, is one of these | Same | Same, plus its owner id |

In the RPC tables below, Human means a human's session (`sock_st_`); a machine key is admitted only where it is named. The token's prefix must match the device's `kind` (`sock_st_` a session, `sock_pt_` a puppet token, `sock_mk_` a machine key); a mismatch is `TOKEN_INVALID`. A `sock_rt_` refresh token or an access JWT presented as a bearer to any RPC is `TOKEN_INVALID`: neither is a device. Connector service tokens (`sock_ct_`) are checked like operator tokens, below, on their own two RPCs. Operator tokens are checked apart from that path: an `OperatorService` RPC accepts only a valid operator token, and refuses everything else (no token, a session or puppet token, or an operator token that is malformed, unknown, expired or revoked) with `CALLER_NOT_ALLOWED`, never `TOKEN_INVALID`, so the reply says nothing about whether a token id exists. An unknown id is still compared against a fixed hash. The refusal has a fixed message and no metadata whatever the cause, and verification is never cached. Exactly one `Authorization` header, scheme `Bearer` and prefix `sock_ot_`, case-sensitive; more than one header is refused. Each failed operator auth takes a token from the caller's service auth bucket (Rate limits); an empty bucket fails `OperatorService` calls from that network `RATE_LIMITED` before any lookup. Logs never carry the `Authorization` header, any part of a token after its id, or an operator request or response body; operator RPCs log procedure, outcome and token id. Every other RPC, the anonymous ones (`SignInOperatorWithApple` too) included, refuses a request bearing a `sock_ot_` token with `CALLER_NOT_ALLOWED` before any lookup. `IssueConnectorPuppetToken` and `RevokeConnectorDevice` accept only a valid `sock_ct_` token, refused the same way (fixed `CALLER_NOT_ALLOWED`, an unknown id compared against a fixed hash, failed auth drawing from the service auth bucket); every other RPC refuses a `sock_ct_` bearer with `CALLER_NOT_ALLOWED` before any lookup. The connector service has no account, so `ACCOUNT_SUSPENDED`, `TERMS_NOT_ACCEPTED` and `SUBSCRIPTION_REQUIRED` reach it only as the grant owner's, listed in its rows. The operator has no account, so `ACCOUNT_SUSPENDED` and `TERMS_NOT_ACCEPTED` never apply to it. Auth middleware resolves every token to a `Principal {accountId, deviceId, kind, ownerId, termsCurrent, proActive}` before any handler runs, refusing a suspended account (or a puppet of one) with `ACCOUNT_SUSPENDED`. `termsCurrent` is the human's own acceptance of the configured terms version (for a machine key, its human's), or for a puppet its owner's. The interceptor then refuses `TERMS_NOT_ACCEPTED` for every RPC not on its explicit exempt list, failing closed for any RPC added later: the exempt RPCs are the reads (`GetMe`, `GetAccounts`, `LookupHandle`, `ListDevices`, `ListPuppets`, `ListConversations`, `MarkRead`, `Subscribe`, `FetchPending`, `Ack`, `ListBlockedAccounts`, `ExportIdentityData`, `ExportMessagingData`), the six `HistoryTransferService` RPCs (they move no content to anyone else), and the safety and exit paths (`AcceptTerms`, `SignOut`, `RevokeDevice`, `ErasePuppet`, `ArchivePuppet`, `EraseAccount`, `Leave`, `RemoveMember`, `BlockAccount`, `UnblockAccount`, `FileReport`, `RegisterPush`, `OpenBillingPortal`, which is how someone cancels Sock Pro, `ListSignInIdentities` and `RemoveEmailSignIn`, how someone finds and removes a sign-in they did not add), and the two connector RPCs (`IssueConnectorPuppetToken`, `RevokeConnectorDevice`), listed because their caller has no account, as `OperatorService` is: `IssueConnectorPuppetToken` checks the grant owner's terms in its handler instead and refuses `TERMS_NOT_ACCEPTED`, since it issues a token as `MintPuppetToken` does; `RevokeConnectorDevice` only removes a credential, an exit path. `MintMachineKey` is not exempt: the key exists to create puppets, which is contact. A machine key's `CreatePuppet` and `MintPuppetToken` are gated on its human's terms like a session's; its `ListPuppets` and `ErasePuppet` are exempt as a read and an exit. Consent (`/oauth/consent` Allow) refuses an owner without current terms, as `CreatePuppet` would. The OAuth routes are not RPCs and pass no interceptor. Sock Pro gate, last, after suspension and terms: when `SOCK_PRO_REQUIRED` is `true` and Sock Pro is not active for the human, or a puppet's owner (`Account.ProActiveUntil()` not after now: no trial, subscription or unrevoked grant keeps it active), every RPC called with a puppet token (the moderation and support puppets excepted) fails `SUBSCRIPTION_REQUIRED`. `CreatePuppet` and `MintPuppetToken` (from a session or a machine key: a key's gate is its human's, so minting from a key never bypasses it), `MintMachineKey`, `IssueConnectorPuppetToken` (the grant owner's) and consent's Allow run `Account.PassProGate()` instead: a human who never had a trial starts their one 7-day trial in the same transaction and passes; otherwise they fail `SUBSCRIPTION_REQUIRED`, and consent's Allow refuses with the "Sock Pro is required" page. Refresh at `/oauth/token` is not gated, since every call the connector puppet makes is, and Pro active again then resumes without a new consent; `Principal` carries `proActive` (gate off, or Pro active). Unset or `false`: off, everyone is active. A `Subscribe` stream re-resolves its `Principal` at every heartbeat and ends with `ACCOUNT_SUSPENDED` once the account is suspended; a puppet's stream also ends with `SUBSCRIPTION_REQUIRED` once its owner's Pro lapses while enforced. Handlers never read ids from the body to decide who the caller is.

## CORS

The web console calls `OperatorService` and `OperatorSignInService` from the browser. `SOCK_CORS_ORIGINS` lists exact allowed origins (comma separated, scheme, host and port, no wildcards). Entries must be exactly `https://host[:port]` (`http://localhost[:port]` off Render); sockd refuses to start otherwise. For an allowed `Origin` on a path starting `/sock.v1.OperatorService/` or `/sock.v1.OperatorSignInService/` (case-sensitive, as the router sees it, on every listener), sockd answers the preflight `OPTIONS` and the `POST` with `Access-Control-Allow-Origin` echoing that origin, `Access-Control-Allow-Methods: POST`, `Access-Control-Allow-Headers: Authorization, Content-Type, Connect-Protocol-Version, Connect-Timeout-Ms`, `Access-Control-Max-Age: 7200`, and never `Access-Control-Allow-Credentials`. Every response on those paths carries `Vary: Origin`. Any other path or origin, or an empty `SOCK_CORS_ORIGINS`, gets no CORS headers, and browsers refuse the call. CORS is not authentication: every `OperatorService` call still needs the operator token, and `SignInOperatorWithApple` an Apple identity token. `SOCK_CORS_ORIGINS` is also the allowlist of return origins for `/apple/console-callback`. `InviteRequestService` has its own allowlist, `SOCK_INVITE_ORIGINS` ([invite-requests](invite-requests.md)); neither list is consulted for the other's paths. `GetRegistrationPolicy` is also allowed for `SOCK_INVITE_ORIGINS`, without credentials, so the website can call it.

## Errors

One closed taxonomy: `ErrorReason` in [`errors.proto`](../../proto/sock/v1/errors.proto), attached as an `ErrorInfo` detail. Each reason has exactly one Connect code, with one exception: `PUSH_TOKEN_IN_USE` is not in the taxonomy as its own reason; the push token already registered to another account answers `FAILED_PRECONDITION` with `FIELD_INVALID`. Every RPC can also return `unavailable` (database or Apple unreachable; retry with backoff) and `internal` (no detail). `TOKEN_INVALID` and `ACCOUNT_SUSPENDED` apply to every authenticated RPC outside `OperatorService` and are not repeated below. `CALLER_NOT_ALLOWED` applies to every RPC (a caller class not listed for it, or an operator token outside `OperatorService`) and is not repeated either. `TERMS_NOT_ACCEPTED` applies to every authenticated RPC not exempt (above); those are marked *terms* below and the reason is not repeated in their rows. `SUBSCRIPTION_REQUIRED` means Sock Pro is not active and the human's one trial is spent; it applies, only while Sock Pro is enforced, to every RPC called with a puppet token and is not repeated; `CreatePuppet`, `MintPuppetToken`, `MintMachineKey` and `IssueConnectorPuppetToken` list it. A machine key gets `CALLER_NOT_ALLOWED` from every RPC but its six, and so does every caller but the connector service from the two connector RPCs. `TOKEN_INVALID` does not apply to the connector RPCs: a bad `sock_ct_` is `CALLER_NOT_ALLOWED`. The OAuth routes answer OAuth errors and pages, not `ErrorReason`s (Operational).

Unknown JSON fields are ignored, not rejected (pinned by `TestUnknownJSONFieldIgnored`).

Clients must decode responses through the Connect codec, which ignores unknown fields, so new response fields stay forward compatible.

## Rate limits

Puppet devices: 60 sends per minute per puppet across `Send` and `NotifyOwner`, token bucket held in Postgres so it holds across replicas. Exceeding it returns `RATE_LIMITED` with `Retry-After` in seconds.

Puppet to owner: a post by a puppet into the direct with its own owner, by `NotifyOwner` or by `Send` into that direct, also draws two buckets, both or neither: 6 an hour per puppet (burst 3) and 20 an hour per owner across all of the owner's puppets (burst 5). The puppet send bucket is drawn first. The moderation and support puppets are exempt; a puppet's posts anywhere else and human posts draw neither. A refusal is `RATE_LIMITED` with `Retry-After` in whole seconds (rounded up, at least 1): the time until both buckets hold a token, absent other spend. A refused post spends nothing and stores nothing. The numbers are placeholders, hub constants.


Solicited replies: a puppet's post into its owner direct draws neither owner-direct bucket when the owner posted into that direct, from any device, less than 15 minutes ago and the puppet has made fewer than 20 such posts since. Each owner post there resets the count. Only the owner's own post into that direct solicits. A solicited post still draws the puppet send bucket. Placeholders, hub constants.

Humans: 120 sends per minute per human across `Send`, same mechanism (a bucket of its own, one per human, not per device).

Account limits, checked under the human's limits lock in the transaction that creates the row and refused `LIMIT_REACHED` (`FAILED_PRECONDITION`) naming the limit, never another account's count: 10 live tokens per puppet (`CreatePuppet` issues the first, `MintPuppetToken` the rest, `IssueConnectorPuppetToken` the connector device), never refused: at 10 the puppet's oldest-issued token other than the connector device is removed first, in the same transaction, except on the moderation and support puppets, which refuse `LIMIT_REACHED` at 10 (the oldest may be the triage agent's); 10 live machine keys per human (`MintMachineKey`). Each is refused until one is revoked or erased. A human has at most 10 live sessions, and sign-in never refuses for it: `SignInWithApple` and `RegisterWithApple` at the limit remove the account's oldest-issued `session` device first, in the same transaction (see `Device.Issue`), so a person left with only stale devices cannot be locked out. The count and the pick are sessions only: a sign-in never evicts a machine key. The moderation and support puppets count toward no limit.

Anonymous callers: 10 calls per minute per client network across `SignInWithApple`, `RegisterWithApple`, `SignInWithEmail`, `RegisterWithEmail` and `SignInOperatorWithApple`. Service-token auth (`sock_ot_` and `sock_ct_`) draws from a service auth bucket per client network of its own, same mechanism and size: every call takes a token, a successful authentication gives it back, and an empty bucket fails the call `RATE_LIMITED` before any lookup. The two buckets are apart, so failed service auth from a shared egress address cannot hold sign-in at `RATE_LIMITED`, and a sign-in flood cannot throttle the operator or `sock-mcpd`. The client address comes from `SOCK_CLIENT_ADDRESS`: `peer` (the connection's own address, the default, for a hub with no proxy in front and for tests) or `header:<name>` (Render). With a header, only the rightmost entry, the one the proxy appended, is used, parsed as an IP. IPv4 is bucketed per /32 and IPv6 per /64; a missing or unparseable value shares one bucket. The limit is never off. `StartEmailSignIn`, `VerifyEmailSignIn` and `SignInWithEmailPassword` also draw per inbox, and `StartEmailSignIn` per client network from a send bucket of its own ([email sign-in, pass 3](email-sign-in-pass-3.md), Rate limits).

Terminal sign-in ([terminal sign-in](terminal-sign-in.md)): `StartTerminalSignIn`, and a `FinishTerminalSignIn` whose token names no live sign-in, draw the anonymous sign-in bucket above. A `FinishTerminalSignIn` that names a live sign-in draws no network bucket: it is paced by the sign-in's own `polled_at`, one call per `poll_interval` (5 seconds), a sooner one `RATE_LIMITED` with `Retry-After` and changing nothing. `POST /login`, `GET /workos/terminal-callback` and `POST /workos/terminal-approve` draw the anonymous network bucket, as the OAuth browser routes do; `GET /login` is static.

`GetRegistrationPolicy` draws from its own limiter, 60 calls per minute per client network per replica, in memory, so website traffic never starves sign-ins behind the same NAT.

Activity: `SetActivity` draws no send bucket. It has its own, 1 a second with burst 3 per (account, conversation), held in each replica's memory, so a caller spread across replicas gets up to that many times the rate. Excess is `RATE_LIMITED` with `Retry-After`. A second bucket per account across all conversations, 5 a second with burst 10, held the same way, is drawn first, so an account cycling conversation ids is refused before any membership lookup.

Exports: `ExportIdentityData` and `ExportMessagingData` 1 an hour per account each, burst 2, held in each replica's memory. Excess is `RATE_LIMITED` with `Retry-After`.

Sign-in identities: `ListSignInIdentities` 1 a minute per account, burst 5, held in each replica's memory, since each call asks WorkOS for the address. Excess is `RATE_LIMITED` with `Retry-After`.

History transfers: `OpenHistoryTransfer` 10 an hour per account, burst 3, and `ClaimHistoryTransfer` 4 an hour per account, burst 2, held in each replica's memory and never persisted. Only a call that creates a transfer or a claim spends a token. Excess is `RATE_LIMITED` with `Retry-After`. Placeholders, hub constants.

Streams: at most 4 open `Subscribe` streams per device on each replica. A fifth ends the device's oldest with `LIMIT_REACHED`. At most 1 open `ReceiveHistory` stream per transfer on each replica: a newer one ends the older with `LIMIT_REACHED`.

Apple identity tokens: every route that verifies one (`SignInWithApple`, `RegisterWithApple`, `SignInOperatorWithApple`, `/apple/oauth-callback`) accepts it once. The hub keeps the token's SHA-256 until the token's `exp` and refuses a second presentation as `APPLE_TOKEN_INVALID`, after every other check, so a replay learns nothing a bad token would not.

Reporters: 10 reports per human per 24 hours (`FileReport`), same mechanism.

Operator erasure: `EraseHuman` draws from one bucket shared by every operator token, 10 an hour, burst 10, same mechanism. A call that erases nothing refunds its draw. Excess is `RATE_LIMITED` with `Retry-After`. Placeholders, hub constants. Operator reads draw nothing.

OAuth, same mechanism, every limit answering `429` with `Retry-After` (an HTTP route) or `RATE_LIMITED` (an RPC). Browser and registration routes, `/oauth/register`, `/oauth/authorize`, `/apple/oauth-callback` (a browser form post) and `/oauth/consent`, draw from the anonymous client network bucket above, shared with the sign-in RPCs. `/oauth/token` and `/oauth/revoke` are reached from the platforms' shared egress addresses, so they never draw per network: each draws from a per-grant bucket (10 per minute, keyed by the grant of the code or refresh token presented) and a per-client bucket (600 per minute, keyed by `client_id`); a request whose token resolves to no grant draws from the client bucket only, and one whose `client_id` is unknown draws from the anonymous network bucket instead, so arbitrary ids create no buckets. A request whose token resolves to no grant also draws from the network bucket, so one network cannot empty a platform's shared client bucket with garbage tokens; a failed request (no grant, or past the grant bucket) refunds the client bucket. A `429` is answered before anything is read or consumed and never counts as a refresh use. The discovery and JWKS routes are static, touch no database and are not rate limited by sockd. `IssueConnectorPuppetToken` and `RevokeConnectorDevice` draw from one bucket per connector service token, 60 per minute; failed `sock_ct_` auth draws from the service auth bucket. Connector puppets keep the puppet send limit.

## MessagingService

Every MessagingService call from a human device first ensures the caller's own participant and endpoint rows exist, from the `Principal` (idempotent upsert). This closes the race where a fresh device calls Messaging before `HumanRegistered` / `DeviceAdded` are consumed. Rows for other accounts come only from events. A self-ensured endpoint takes `issued_at` from the `Principal`'s device `created_at` and backfills like the `DeviceAdded` projection (events.md, the Identity watermark).

An active puppet is the moderation or support puppet, or a puppet that is not archived, neither it nor its owner suspended, whose owner has Sock Pro (always, while `SOCK_PRO_REQUIRED` is off). A human posts only into a conversation with one; Messaging decides from its own projections of `ProEntitlementChanged`, `AccountSuspensionChanged` and `PuppetArchiveChanged` (events.md). Membership changes are never refused for it.

## OperatorService

Every RPC: caller class operator, authenticated by a valid operator token (see Caller classes); anything else is `CALLER_NOT_ALLOWED`, and `RATE_LIMITED` once failed operator auth from the caller's network has emptied its bucket. Each calls the aggregate method its `sockd` counterpart calls, so the CLI and the network cannot drift apart in behavior. Every successful call, no-ops included, writes one `OperatorAction` (token id, action, time, target) in its own transaction; the reads (`ListReports`, `ListHumans`, `GetHuman`, `ListAccountReports`, `ListInviteRequests`, `VerifyTriageToken`) write none. `ApproveInviteRequests` and `DeclineInviteRequests` write one per request they change, in that request's transaction, and none for a no-op.

Scope: a `read` operator token reaches only `ListReports`, `GetFeatureFlags`, `ListInviteRequests` (never with codes) and `RevokeOperatorToken` (the Users RPCs are `full` only); every other RPC here refuses it with `CALLER_NOT_ALLOWED` after authentication. A `triage` token reaches only `VerifyTriageToken` and `RevokeOperatorToken`, and `VerifyTriageToken` admits only `triage` ([triage tokens](triage-tokens.md)). The console's `SignInOperatorWithApple` mints `full`.

Terms gate: the twenty-three procedures are listed in the server's terms exempt list (`api.TermsExemptProcedures`), deliberately. The gate fails closed for unlisted procedures and is written for account principals; the operator has no account and no terms, so its procedures are exempt by listing rather than by a special case in the gate. That is safe because they admit no account caller. A server test asserts every `OperatorService` procedure is on the list. Request and response fields: [`operator.proto`](../../proto/sock/v1/operator.proto).

A mint reachable with an operator token would let a leaked token perpetuate itself; the one network mint of a `full` token, `SignInOperatorWithApple`, takes an Apple identity instead and is the console's daily path, with these commands as break-glass. `MintTriageToken` mints under an operator token but cannot perpetuate one: its token expires no later than its parent, reaches no RPC that reads or acts, and goes when its parent is revoked.

## OperatorSignInService

Sign in with Apple for the console and `sock-admin`. Anonymous: no `Authorization` header (a `sock_ot_` bearer is `CALLER_NOT_ALLOWED`, as for every non-operator RPC). Kept apart from `OperatorService`, whose every RPC still requires an operator token. Listed with the anonymous procedures in the auth interceptor and in `api.TermsExemptProcedures` (it admits no account). Logs procedure and outcome, and on success the minted token id; never the identity token, the nonce or the Apple `sub`. Request and response fields: [`operator.proto`](../../proto/sock/v1/operator.proto).

## HistoryTransferService

Moves a phone's local history to a newly signed-in desktop of the same human, once, through the hub, sealed to a key only the desktop holds ([history transfer](history-transfer.md)). Human device only: desktop and phone are both human sessions and the hub cannot tell which is which. Anonymous: `TOKEN_INVALID`. Puppet: `CALLER_NOT_ALLOWED` from the handler (`IsPuppet`), since the interceptor has no puppet refusal; with the Pro gate on, a puppet whose owner lacks Pro gets `SUBSCRIPTION_REQUIRED` from the interceptor first. Machine key and every other class: `CALLER_NOT_ALLOWED`. Terms-exempt (it moves no content to anyone else) and not Pro-gated. Its own `ReadMaxBytes` of 1 MiB + 64 KiB, since the default 128 KiB cannot carry a chunk. Every lookup is by the binding tag, `HMAC-SHA-256(key = transfer secret, msg = "sock history transfer v1" ‖ caller's account id as 16 UUID bytes)`, which the hub computes from the authenticated caller and the presented secret and never accepts from a client: an unknown, expired, closed or other human's transfer is the same `NOT_FOUND`. `transfer_secret` is always exactly 32 bytes, else `FIELD_INVALID`. Every RPC can also return `unavailable`. No new `ErrorReason`. Logs procedure and status code only, never a body (every one carries the secret), an id, a tag or a size. Request and response fields: [`history_transfer.proto`](../../proto/sock/v1/history_transfer.proto).

## Coverage

- Every caller class reaches at least one RPC or route: Stripe (`POST /stripe/webhook` only), anonymous (9: the five sign-in RPCs, `StartTerminalSignIn`, `FinishTerminalSignIn`, `RequestInvite` and `GetRegistrationPolicy`, and the OAuth discovery and JWKS routes, `GET /login` and `GET /download/<key>`), human (all but `NotifyOwner`, the two connector RPCs and `OperatorService`), puppet (11, not `MarkRead` or `HistoryTransferService`), machine key (6: `CreatePuppet`, `ListPuppets`, `MintPuppetToken`, `ErasePuppet`, `ArchivePuppet`, `UnarchivePuppet`), OAuth client (`/oauth/register`, `/oauth/token`, `/oauth/revoke` and discovery), consenting browser (`/oauth/authorize`, `/apple/oauth-callback`, `/oauth/consent`), signing-in browser (`/login`, `/workos/terminal-callback`, `/workos/terminal-approve`), connector service (2: `IssueConnectorPuppetToken`, `RevokeConnectorDevice`), operator (21, `OperatorService` only; it reaches `OperatorSignInService` as anonymous, before it holds a token).
- Every *terms* RPC is one that creates content or contact. Reading, leaving, blocking, reporting, exporting, erasing and accepting terms stay open without current terms. `IssueConnectorPuppetToken` checks the grant owner's terms in its handler; its caller has none.
- No RPC admits a class outside this table. A caller class not listed for an RPC gets `CALLER_NOT_ALLOWED`.
